# DimVibe — единая инструкция по проекту

**Статус:** архитектурная спецификация для разработки с нуля.  
**Обновлено:** 14 октября 2026 г.  
**Назначение:** передать контекст проекта разработчику или AI-агенту, сохранить утверждённые решения, отделить их от предложений и открытых вопросов.  
**Важно:** это документ проектирования, а не описание уже реализованных возможностей.

## 1. Цель и принципы

DimVibe — модульная платформа создания интерактивных учебных упражнений (прежде всего языковых). Преподаватель создаёт упражнения в **Author Studio**, публикует их и вставляет в LMS (в частности LearnWorlds) по постоянной ссылке/iframe. Ученик выполняет их в едином **Player**, который подключает независимые типы упражнений.

Приоритеты:

1. Начать **новую кодовую базу с нуля**; прежний прототип Google AI Studio использовать только как визуальный/функциональный референс. Не переносить накопленные версии, исправления и старый код автоматически.
2. Простой и надёжный MVP, единые контракты, независимые модули, минимальная связность.
3. Сначала работающий вертикальный сценарий, затем расширение.
4. Не превращать мелкие UI-сценарии в блокирующие архитектурные решения: спорные детали проверять прототипом.
5. Не считать выбор **Google AI Studio / Codex / Claude Code** утверждённым: рабочий процесс будет решаться отдельно.

## 2. Терминология

- **Exercise** — упражнение со стабильным ID.
- **Module** — тип упражнения (Fill Blanks, Image to Gaps, Matching и т. д.).
- **Author Studio** — Dashboard, Library, Editor, Preview, настройки.
- **Player Core** — единый жизненный цикл выполнения, проверки, попытки, итог, перезапуск.
- **moduleData** — специфические данные конкретного модуля.
- **Draft** — редактируемый черновик.
- **Published Version** — неизменяемый снимок упражнения, доступный ученику.
- **publishedVersionId** — указатель на актуальную опубликованную версию.
- **Check** — успешный запуск оценивания (не обязательно правильный ответ); неверифицируемое/неполное состояние не расходует проверку.
- **Run / прохождение** — одно открытие/выполнение упражнения до завершения или сброса.

## 3. Утверждённая архитектура

### 3.1. Схема упражнения

Единая **версионированная схема** с общими разделами:

- `content` — название, инструкции, текст и общие материалы;
- `design` — тема, визуальные настройки;
- `behavior` — правила прохождения и проверок;
- `publication` — сведения о публикации (конкретное разделение метаданных упражнения и записи публикации уточнить при реализации);
- `moduleData` — специфическая структура модуля;
- общие поля идентификатора, `schemaVersion`, `module`, версии.

Пример **иллюстративный, не окончательная JSON Schema**:

```json
{
  "id": "exercise_001",
  "schemaVersion": 1,
  "module": "fill-blanks",
  "content": { "title": "Exercise", "instructions": "Fill in the blanks" },
  "design": { "theme": "classic" },
  "behavior": { "maxAttempts": 5 },
  "publication": {},
  "moduleData": { "mode": "word-bank", "items": [] }
}
```

Не следует дублировать внутренние структуры каждого модуля в Player Core.

### 3.2. Реестр независимых модулей

**Утверждено:** модули подключаются к Player Core через единый интерфейс и внутренний реестр; Core выбирает модуль по `exercise.module`. Не строить преждевременно сложный внешний marketplace/plugin runtime.

Концептуально:

```ts
const modules = {
  'fill-blanks': FillBlanksModule,
  'image-to-gaps': ImageToGapsModule,
  'matching': MatchingModule,
};
```

Общие функции — в Core; ввод, размещение, структура ответов, оценивание — в модуле.

### 3.3. Владение состоянием ответов

**Утверждено:** модуль управляет структурой и изменениями ответов ученика. Core может получить сериализуемый снимок и восстановить его через единый интерфейс, **но в утверждённой упрощённой модели восстановление после перезагрузки не используется**. Не строить сложную инфраструктуру хранения только ради потенциального будущего восстановления.

Core не интерпретирует специфические ответы (например, координаты/ID изображений в пропусках).

### 3.4. Проверка и оценивание

**Утверждено:** модуль проверяет готовность (`validate`) и оценивает (`evaluate`), возвращая стандартизированный результат. Core отвечает за число проверок, историю текущего прохождения, итоговые баллы, процент, завершение и общую визуализацию.

Минимальный утверждённый контракт элемента:

```ts
type CheckItem = {
  id: string;
  score: number;
  maxScore: number;
};

type CheckResult = {
  items: CheckItem[];
};
```

- Статус определяется автоматически: `score === maxScore` — верно, `score === 0` — неверно, промежуточное значение — частично верно (для `maxScore > 0`).
- Core суммирует `score`/`maxScore` и рассчитывает процент. Округление процента — математическое до целого для отображения; внутреннее значение сохранять точно.
- Модуль отображает локальную подсветку ответов по результату.
- `validate()` отдельно определяет, можно ли проводить проверку. При неполных обязательных ответах показывать причину и количество незаполненных, **не расходовать проверку**.
- Для Image to Gaps каждый пропуск даёт 1/0; для других модулей возможна собственная схема и частичные баллы, совместимые с общим контрактом.
- Конкретные сигнатуры API, обработка ошибок и защитные проверки чисел должны быть оформлены при реализации.

### 3.5. Упрощённая модель прохождения — последняя утверждённая редакция

**Эти решения заменяют прежнюю сложную схему сессий/восстановления/истории множества прохождений.**

- `maxAttempts` = **1–5**, по умолчанию **5**; преподаватель выбирает в **Editor → Поведение**.
- Неограниченных проверок нет.
- Проверка расходуется **только если действительно выполнено оценивание**; пустые/недопустимые ответы не расходуют её.
- Успешное выполнение всех оцениваемых элементов завершает упражнение досрочно.
- Пятая (или установленная последняя) проверка завершает прохождение, даже если ответы не все правильные.
- После завершения доступны итог и **«Начать заново»** — новый чистый проход.
- **Перезагрузка страницы/самого упражнения начинает заново**: ответы, попытки, результаты и история текущего прохождения сбрасываются.
- **Нет восстановления незавершённого прогресса после перезагрузки**, нет истории множества завершённых прохождений, нет механизма «непрочитанных» старых результатов.
- Можно хранить историю **проверок только текущего прохождения**, максимум 5.
- Текущее состояние может находиться в оперативной памяти. Не проектировать `sessionStorage` и межвкладочную синхронизацию как обязательные компоненты MVP.
- Если после неправильной проверки повторное оценивание допускается только после изменения ответа — это ранее принятое правило Image to Gaps; применять к другим модулям по согласованному контракту, не усложняя Core.

Пример жизненного цикла: `START → IN_PROGRESS → COMPLETED → RESTART`.

### 3.6. Публикация и версии

**Утверждено:**

- У упражнения **постоянный адрес и iframe-код**.
- Редактирование Draft не меняет опубликованное упражнение.
- Повторная публикация создаёт **новую неизменяемую версию** и обновляет `publishedVersionId`.
- Player при **новой загрузке** открывает текущую опубликованную версию; уже открытое прохождение не переключается на новую версию посреди работы.
- Editor показывает историю публикаций.
- **Откат** реализуется выбором ранее опубликованной неизменяемой версии и обновлением `publishedVersionId`, без изменения публичной ссылки.
- Сравнение/слияние веток версий, сложный журнал действий — не требования MVP.
- При перезагрузке открывается актуальная опубликованная версия и начинается новый проход.

**Важно:** история опубликованных **версий преподавателя** сохраняется; история завершённых **прохождений ученика** — нет. Это разные сущности.

### 3.7. Ограничение числа пропусков

**Утверждено:** не более **10 пропусков на одно упражнение** в Fill Blanks, Words to Gaps и Image to Gaps. Ограничение применяется в **Editor**, а не в Player. При превышении Editor предлагает разделить текст по смысловым границам (предложения/абзацы) на самостоятельные упражнения, сохраняя ответы и содержание. Каждое новое упражнение имеет независимые проверки, банк и результаты. Для других модулей лимиты определить отдельно.

## 4. Author Studio и Editor

- Главная: создание упражнений, библиотека, настройки; карточки модулей, категории, избранное и сортировка — предусмотренные возможности.
- Editor имеет четыре вкладки: **Содержимое**, **Дизайн**, **Поведение**, **Публикация**.
- Preview для проверки упражнения до публикации, включая разные размеры экрана.
- Черновики, автосохранение, Undo/Redo, явная повторная публикация; история опубликованных версий.
- Языки интерфейса: **EN / RU / KA**. Локализация содержимого и сообщений преподавателя отделяется от локализации системного интерфейса.
- Темы: **Classic** и **Comic**; адаптивность, настройка шрифтов/масштаба, доступность.
- DEMO MODE для модулей: образец упражнения, возможность изменять, сбрасывать, сохранить как собственный черновик.
- Rich text в инструкциях и материалах, форматирование сохраняется в Player и iframe.
- **Teacher’s Note** — необязательная заметка под упражнением, иконка и режим показа (всегда / после проверки / по нажатию).
- Дальнейшие расширения: коллекции упражнений, стартовые/финальные экраны, аудио, объяснения, анимации, рандомизация там, где применимо.

## 5. Player — общие интерфейсные правила (ранее согласованные; не блокировать MVP микродеталями)

- Единый каркас всех модулей: заголовок, инструкции, центральная область упражнения, проверки, результат, перезапуск.
- Компактный sticky header внутри Player/iframe; не перекрывать родительский LearnWorlds. На мобильном — название и единое меню вместо множества кнопок.
- Header скрывается при прокрутке вниз, возвращается при достижении верха (с учётом reduced motion).
- Общая нижняя панель с **«Проверить»**, прогрессом и оставшимися проверками; на мобильном при открытой клавиатуре компактная адаптация.
- «Проверить» остаётся доступной до завершения; при неполных обязательных ответах — предупреждение, **без расхода попытки**.
- Для упражнений с пропусками предусмотрено «Перейти к пропуску» / «Найти пропуски · N», навигация «Назад/Далее» по незаполненным, подсветка выбранного пропуска. Переходы только по действию пользователя; не открывать клавиатуру автоматически и не прокручивать родительскую страницу iframe.
- Выбранный пропуск выделяется контрастным контуром и мягким фоном, независимо от красной/зелёной подсветки оценки и клавиатурного фокуса.
- При заполнении не выполнять автоматический переход. Навигация нециклическая; закрывается вручную или после заполнения всех пропусков.
- Скролл к пропуску — внутри Player, с отступом от sticky-элементов; учитывать `prefers-reduced-motion`.
- Итог показывается встроенным блоком ниже упражнения: правильные/неправильные, проверки, процент и прогресс. На 100% допускается короткая тематическая анимация с reduced motion; при ошибках — нейтральная поддерживающая подача.
- История **проверок текущего прохода** может отображаться в блоке результата. Ранее детально спроектированная история многих прохождений, аккордеоны и счётчики «Новое» **отменены новой упрощённой моделью**. Размещение пункта «История» в header пересмотреть в MVP: он не обязателен.

## 6. Модули

### 6.1. Fill Blanks

- Режимы упражнений: отдельные предложения и связный текст.
- Пропуски создаются выделением слова/фразы или нажатием на слово; защищённые атомарные элементы с контекстным редактированием.
- Ответы, альтернативные варианты, подсказки; сравнение без учёта регистра, с обрезкой краевых пробелов и нормализацией лишних пробелов.
- Шесть взаимоисключающих режимов на одно упражнение (не смешивать в v1):
  1. Свободный ввод текста.
  2. Ввод с автоматическим словарным банком.
  3. Перетаскивание/нажатие по банку слов.
  4. Выпадающий список.
  5. Image to Gaps.
  6. Image Hint + Text Input — изображение над полем ввода внутри компактного inline-элемента.
- Автоматическое формирование банка, опциональные отвлекающие элементы; использованные экземпляры неактивны до возврата, возможность замены.
- Перемешивание банка при новом прохождении, порядок стабилен внутри текущего прохода; Retry сохраняет порядок банка по ранее принятому поведению (при перезагрузке новый порядок возможен).
- Три визуальных стиля пропусков, адаптивные размеры, переносы без разрыва составных элементов, специальные символы.
- Для отдельных предложений — не более одной необязательной иллюстрации на предложение, с настройками изображения.
- Быстрая вставка текста v1: разметка пропусков вручную, без обязательной AI-авторазметки; авторазделение на карточки предложений, редактирование границ; добавление/замена с предупреждением и Undo.

### 6.2. Image to Gaps

**Контент и банк**

- Каждый пропуск имеет назначенное правильное изображение; отвлекающие изображения собираются в общий банк упражнения.
- Общая медиабиблиотека DimVibe для повторного использования изображений между модулями.
- Одно изображение может быть правильным в нескольких пропусках: создавать отдельный экземпляр в банке на каждое требуемое размещение.
- Изображение может одновременно использоваться как правильное и как ловушка при соответствующей конфигурации.
- В Editor единая сетка банка с фильтрами «Все», «Ответы», «Ловушки»; маркировка ответов только для автора. Ученик не видит меток правильности.
- Добавление ловушек через контекст пропуска или общий банк; множественный выбор из медиабиблиотеки.
- Карточки изображений: `contain` по умолчанию, опционально `cover`; внутри пропуска изображение остаётся читаемым, элемент переносится целиком.
- Замена изображения сохраняет назначение, позицию, оформление и Undo; если изображение используется в нескольких местах, можно заменить в одном или во всех.
- Удаление назначенных изображений защищено; массовое удаление — только неназначенных с подтверждением.
- Перемешивание банка только при новом прохождении, без перемешивания во время выполнения; при «Начать заново» по ранее согласованному UX порядок банка сохраняется, но обновление страницы создаёт новое прохождение и может применить новое перемешивание.

**Действия ученика**

- Выбор доступной картинки подсвечивает все пустые пропуски одинаково, не раскрывая правильные.
- Нажатие на пустой пропуск размещает выбранную картинку; выбор сбрасывается.
- Использованная картинка остаётся на прежнем месте в банке приглушённой и недоступной; возвращается только через заполненный пропуск.
- Нажатие на заполненный пропуск без выбранной картинки возвращает изображение; с выбранной новой — заменяет в одно действие. Перетаскивание тоже поддерживает замену.
- Повторный выбор карточки, Esc или нажатие вне интерактивных элементов отменяют выбор; обычный скролл не отменяет.
- После неправильной проверки картинки остаются в пропусках и доступны для исправления до завершения. Исправление сбрасывает старую ошибочную подсветку до следующей проверки.
- Клавиатурное управление: Tab/Shift+Tab, Enter/Space, Esc; не переносить фокус автоматически неожиданным образом.
- Неполные ответы не проверяются и не расходуют попытку; повторная проверка после неудачи требует изменения ответа. На последней проверке прохождение завершается и ответы блокируются.
- Опциональное раскрытие правильных ответов после завершения: показывать правильное изображение рядом с ошибочным только для неправильных пропусков, с переключателем видимости; результат не меняется.
- «Начать заново» очищает ответы, подсветку, проверки и результат без подтверждения; фокус и скролл возвращаются к началу упражнения внутри iframe.

**Сообщения и результаты**

- Сообщения успеха/неуспеха настраиваются в Editor → Поведение → Завершение; базовое форматирование (жирный, курсив, переносы, ссылки), локализованные значения RU/EN/KA с fallback.
- Балл каждого пропуска: 1/0; общий процент рассчитывает Core.

### 6.3. Другие модули

- **Words to Gaps** — модуль пропусков со словами, подчиняется лимиту 10 пропусков.
- **Matching**, **Sorting**, **ABCD**, **Color Coding** — запланированные типы; должны использовать общий контракт, но сохранять собственные `moduleData`, состояние ответов и оценивание.
- Не утверждать детальную структуру этих модулей до отдельного проектирования/прототипа.

## 7. LearnWorlds, ссылки и безопасность

- Упражнение должно корректно встраиваться в LearnWorlds через iframe, включая мобильные размеры, прокрутку, sticky-элементы, фокус, клавиатуру и ограничение прокрутки родительской страницы.
- Публичный Player получает **опубликованную версию**, а не редактируемый черновик.
- Старые сценарии сохранения прогресса по `instanceId`, блокировки дубликатов iframe, lease/ownership и синхронизации вкладок **больше не нужны для восстановления ученической сессии в MVP**; не переносить их как обязательную инфраструктуру.
- Защита прав на изменение черновиков и публикаций, проверка входных данных и безопасная обработка загруженных изображений остаются обязательными техническими требованиями; конкретная реализация зависит от выбранного стека.
- Если понадобится LMS gradebook/передача оценок, это **отдельная будущая интеграция**, не предполагать, что один iframe автоматически записывает оценки в LMS.

## 8. Рекомендуемый технический каркас — НЕ утверждён как стек

Возможная организация:

```text
dimvibe/
  apps/
    studio/
    player/
  packages/
    contracts/
    player-core/
    ui/
    modules/
      fill-blanks/
      image-to-gaps/
      matching/
      ...
  services/
    publication/
    media/
```

Это **логические границы**, не требование отдельных серверов, монорепозитория или конкретного фреймворка. Для MVP сервисы публикации и медиабиблиотеки могут жить в одном backend.

Предполагаемые компоненты данных:

- Exercise: стабильный ID, владелец, метаданные, ссылка на Draft, `publishedVersionId`.
- Draft: изменяемая версия авторских данных.
- PublishedVersion: immutable snapshot, версия схемы, номер/ID публикации, время публикации.
- MediaAsset: файл, метаданные, права доступа, ссылки на использование.
- Ученические ответы/попытки: в памяти текущего Player, без постоянной истории по умолчанию.

Это концептуальная модель; точные таблицы/коллекции и API — после выбора инструментов.

## 9. Предлагаемый план MVP — не утверждённый график

1. Создать чистый репозиторий и зафиксировать контракт данных, интерфейс модулей, правила изменений.
2. Реализовать минимальный Player Core и тестовый модуль на локальных данных.
3. Реализовать один полный вертикальный сценарий **Fill Blanks**: Editor → Preview → Publish → Player → Check → Restart.
4. Подключить постоянную ссылку, неизменяемые версии, историю публикаций и откат.
5. Добавить Image to Gaps и общую медиабиблиотеку.
6. Проверить LearnWorlds iframe, мобильные устройства, доступность и регрессионные тесты.
7. Подключать другие модули по тому же интерфейсу.

**Критерии первой технической проверки:** Core не содержит специфической логики ответов, новая версия не меняет открытое прохождение, проверка неполного упражнения не тратит попытку, 1–5 проверок работают, обновление сбрасывает, опубликованная ссылка стабильна, откат работает.

## 10. Открытые решения — не принимать за утверждённые

1. **Основная среда разработки:** Google AI Studio, Codex или Claude Code; один или несколько инструментов, процесс передачи задач и ревью. Пользователь прямо отложил выбор до следующего этапа.
2. **Git и репозиторий:** рекомендован как единый источник кода, но конкретный провайдер и workflow ещё не утверждены.
3. **Технологический стек:** React/TypeScript, backend, Firebase/Google Cloud, hosting, auth и т. д. — только варианты, не решение.
4. **Модель хранения и доступов:** конкретная БД, роли, права, файловое хранилище, правила удаления и лимиты.
5. **Точные API и JSON Schema:** валидаторы, миграции `schemaVersion`, структура moduleData каждого модуля, обработка ошибок.
6. **Публичный доступ:** видимость упражнений, авторизация, режимы preview и опубликованной ссылки.
7. **Экспорт оценок в LMS:** необходимость и механизм отдельно.
8. **Приоритет остальных модулей и точный состав первого релиза.**
9. **UI-детали**, не влияющие на архитектуру: окончательное место истории текущих проверок, мобильные состояния, микровзаимодействия.
10. **Оценка неполного/частично правильного ответа** для модулей кроме утверждённых правил Image to Gaps.

## 11. Правила для AI-разработчика / команды

1. **Не использовать старый код прототипа как основу без нового явного разрешения.** Существующий проект — референс по функциям и визуалу.
2. Считать разделы «Утверждено» источником требований. Не превращать предложения из разделов 8–10 в обязательные решения.
3. Любые изменения утверждённой логики сначала согласовывать; явно фиксировать, какое прежнее решение заменено.
4. Не создавать сложное хранение ученических сессий, историю нескольких прохождений или межвкладочную блокировку: они отменены.
5. Не создавать единый монолитный `switch` с бизнес-логикой всех модулей внутри Player Core.
6. Проверять данные на границах Editor → Publication → Player, не доверять содержимому публикации без валидации.
7. Делать небольшие проверяемые изменения, тесты контрактов, воспроизводимые сборки и понятную историю коммитов после выбора Git workflow.
8. Сначала реализовать один рабочий сквозной сценарий, потом обобщать и расширять.
9. Учитывать RU/EN/KA, грузинские шрифты, мобильный iframe, клавиатурное управление и reduced motion.
10. При сомнении обозначать **«утверждено / предложено / открытый вопрос»**; не выдавать план за реализованный код.

## 12. Сводка последних решений и приоритетов

- Новая реализация DimVibe **с нуля** — утверждено.
- Унифицированная версия схемы упражнения + `moduleData` — утверждено.
- Реестр независимых модулей и единый Player Core — утверждено.
- Состояние ответов принадлежит модулю — утверждено.
- `validate()`/`evaluate()`, результат `{id, score, maxScore}` — утверждено.
- 1–5 проверок, по умолчанию 5, без unlimited — утверждено.
- Перезагрузка = сброс, нет сохранения незавершённого прогресса и истории многих прохождений — утверждено; заменяет старую модель.
- Лимит 10 пропусков в Editor — утверждено.
- Постоянная ссылка/iframe, immutable PublishedVersion, история публикаций и откат — утверждено.
- Выбор AI-инструмента и рабочего процесса — **отложен**.
