# Пользователи, роли и права доступа DimVibe

**Статус:** двухролевая модель — APPROVED (2026-10-14). Детали реализации и дополнительные защитные механизмы — PROPOSED, пока не утверждены отдельно.

## Утверждённые правила

- Ровно две базовые роли: **Administrator** и **Teacher**.
- Administrator имеет полный контроль над платформой: видит, создаёт, изменяет, публикует, удаляет и восстанавливает любые упражнения и ресурсы; управляет пользователями и глобальными настройками.
- Teacher видит и управляет **только своими** упражнениями, черновиками, публикациями, изображениями и материалами. Может удалять только собственные ресурсы.
- Teacher работает с доступными модулями, Editor и Player, но не управляет чужими данными или глобальной конфигурацией.
- Роли действуют в **одном приложении**, с общими Editor Core, Player Core и модулями. Дублировать редактор для администратора нельзя.
- Несколько преподавателей имеют индивидуальные аккаунты и независимые библиотеки (D-020).

## Матрица разрешений (APPROVED)

| Операция | Administrator | Teacher |
|---|---|---|
| Список и просмотр упражнений | Все | Только свои |
| Создание упражнения | Да | Да, в свою библиотеку |
| Изменение Draft | Любого | Только своего |
| Дублирование | Любого | Только своего |
| Удаление и восстановление | Любого | Только своего |
| Публикация и откат | Любого | Только своего |
| Изображения и материалы | Все | Только свои |
| Управление пользователями/ролями | Да | Нет |
| Глобальные настройки платформы | Да | Нет |
| Настройки собственного упражнения | Да | Да |

## Проектные правила безопасности (PROPOSED)

- Проверять роль и владение ресурсом **на сервере для каждой операции**, а не только скрывать UI.
- Идентичность и роль брать из проверенной сессии, не доверять `role`/`ownerId` в клиентском запросе.
- Для всех приватных сущностей (exercise, draft, published version, media) обеспечивать привязку к владельцу.
- Административные действия с чужими ресурсами фиксировать в журнале аудита.
- Не допускать удаления/отключения последнего активного администратора.
- Отключение Teacher не должно автоматически удалять опубликованные версии или медиа.
- Доступ к публичному Player и разрешённым опубликованным медиа проектировать отдельно от доступа к приватной библиотеке.

## Приёмочные тесты

- Teacher A не видит ресурсы Teacher B ни в UI, ни через прямой запрос API.
- Teacher A не может изменить `ownerId` в запросе и получить доступ к B.
- Teacher не может вызвать администраторские операции через прямой API.
- Administrator может найти, изменить, опубликовать и удалить материал любого Teacher.
- Изменение общей части Editor Core отображается одинаково в интерфейсах обеих ролей.
- Приватное изображение Teacher B не доступно Teacher A через прямую ссылку или API.

## Открытые решения

- Метод входа и регистрации; кто создаёт Teacher-аккаунты.
- Правила публичного Player без аккаунта ученика.
- Политика удаления опубликованного упражнения и корзины.
- Аудит, защита последнего администратора и жизненный цикл отключённых аккаунтов — предложены, но не утверждены.
