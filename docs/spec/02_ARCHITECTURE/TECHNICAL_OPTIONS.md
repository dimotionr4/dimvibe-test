## 8. Рекомендуемый технический каркас — НЕ утверждён как стек

Возможная организация:

```text
dimvibe/
  apps/
    studio/
    player/
  packages/
    contracts/
    player-core/
    ui/
    modules/
      fill-blanks/
      image-to-gaps/
      matching/
      ...
  services/
    publication/
    media/
```

Это **логические границы**, не требование отдельных серверов, монорепозитория или конкретного фреймворка. Для MVP сервисы публикации и медиабиблиотеки могут жить в одном backend.

Предполагаемые компоненты данных:

- Exercise: стабильный ID, владелец, метаданные, ссылка на Draft, `publishedVersionId`.
- Draft: изменяемая версия авторских данных.
- PublishedVersion: immutable snapshot, версия схемы, номер/ID публикации, время публикации.
- MediaAsset: файл, метаданные, права доступа, ссылки на использование.
- Ученические ответы/попытки: в памяти текущего Player, без постоянной истории по умолчанию.

Это концептуальная модель; точные таблицы/коллекции и API — после выбора инструментов.

Не начинать реализацию по этой структуре до согласования технологического стека.
