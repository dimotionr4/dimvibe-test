## 11. Правила для AI-разработчика / команды

1. **Не использовать старый код прототипа как основу без нового явного разрешения.** Существующий проект — референс по функциям и визуалу.
2. Считать разделы «Утверждено» источником требований. Не превращать предложения из разделов 8–10 в обязательные решения.
3. Любые изменения утверждённой логики сначала согласовывать; явно фиксировать, какое прежнее решение заменено.
4. Не создавать сложное хранение ученических сессий, историю нескольких прохождений или межвкладочную блокировку: они отменены.
5. Не создавать единый монолитный `switch` с бизнес-логикой всех модулей внутри Player Core.
6. Проверять данные на границах Editor → Publication → Player, не доверять содержимому публикации без валидации.
7. Делать небольшие проверяемые изменения, тесты контрактов, воспроизводимые сборки и понятную историю коммитов после выбора Git workflow.
8. Сначала реализовать один рабочий сквозной сценарий, потом обобщать и расширять.
9. Учитывать RU/EN/KA, грузинские шрифты, мобильный iframe, клавиатурное управление и reduced motion.
10. При сомнении обозначать **«утверждено / предложено / открытый вопрос»**; не выдавать план за реализованный код.


## Шаблон запроса на разработку

**ID задачи:** TASK-...  
**Цель:** одна проверяемая возможность.  
**Владелец требований:** путь к одному нормативному документу.  
**Обязательные зависимости:** CONTRACTS + нужный Core + нужный модуль.  
**Что НЕ менять:** соседние модули, публичные контракты без отдельного согласования.  
**Критерии приёмки:** конкретные наблюдаемые результаты.  
**Тесты:** unit/contract/integration по характеру задачи.  
**Результат:** изменённые файлы, краткое описание, результаты тестов, известные ограничения.

## Защитные правила

- Не отправлять задачу «реализуй всю платформу по всем MD».
- При противоречии остановиться и открыть вопрос, не выбирать молча.
- Не переписывать общий Core ради локальной функции без архитектурного обоснования.
- Перед изменением общего компонента оценить влияние на все модули-потребители.
- Не считать выполненным то, что не проверено тестом/демонстрацией.
