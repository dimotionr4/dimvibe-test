## 9. Предлагаемый план MVP — не утверждённый график

1. Создать чистый репозиторий и зафиксировать контракт данных, интерфейс модулей, правила изменений.
2. Реализовать минимальный Player Core и тестовый модуль на локальных данных.
3. Реализовать один полный вертикальный сценарий **Fill Blanks**: Editor → Preview → Publish → Player → Check → Restart.
4. Подключить постоянную ссылку, неизменяемые версии, историю публикаций и откат.
5. Добавить Image to Gaps и общую медиабиблиотеку.
6. Проверить LearnWorlds iframe, мобильные устройства, доступность и регрессионные тесты.
7. Подключать другие модули по тому же интерфейсу.

**Критерии первой технической проверки:** Core не содержит специфической логики ответов, новая версия не меняет открытое прохождение, проверка неполного упражнения не тратит попытку, 1–5 проверок работают, обновление сбрасывает, опубликованная ссылка стабильна, откат работает.

## Общие проверки регрессий

1. Общая правка Editor Core видна всем модулям-потребителям.
2. Специфическая правка одного Module Editor не меняет другой.
3. Player Core не импортирует бизнес-логику модулей.
4. Invalid `validate` не тратит проверку.
5. Последняя допустимая проверка завершает проход.
6. Reload начинает чистый проход.
7. Draft не меняет опубликованную версию.
8. Rollback сохраняет URL и iframe.
9. Ограничение 10 пропусков обеспечивается Editor.

## Уточнение после утверждения MVP (D-018/D-019)

Все пакеты должны покрыть M01–M29 из `MVP_SCOPE.md`; приёмка по AC-01–AC-32 из `ACCEPTANCE_CRITERIA.md`. Не считать TASK-005 готовым, если в Fill Blanks реализован только один из трёх утверждённых способов ответа. Не считать TASK-007 готовым без переиспользования Media Library. Рекомендуемый порядок — **постепенная реализация внутри полного MVP**, не сокращение объёма.

**Предварительные подзадачи:** контракт модулей → Gap Engine → Editor/Player shell → Draft/Undo/Preview → Fill Blanks (typing, bank, dropdown) → Publication → Media Library → Image to Gaps → темы/локализация/адаптивность → регрессионные тесты и iframe. Допускается иной порядок после выбора стека, если зависимости соблюдены.

## Пакет проектирования хранилища (PROPOSED)

- **TASK-DATA-01**: утвердить OQ-DATA-01…05, затем определить схемы сущностей и индексы. **Приёмка:** Draft, PublishedVersion, Pointer и MediaAsset имеют разные права/жизненные циклы.
- **TASK-DATA-02**: реализовать сохранение Draft с ревизией. **Приёмка:** закрытие/открытие Editor восстанавливает черновик; конкурентное сохранение не затирает его молча.
- **TASK-DATA-03**: реализовать атомарную публикацию/откат. **Приёмка:** сбой не меняет активную версию; публикация/откат сохраняют URL; открытый Player не переключается.
- **TASK-DATA-04**: связать MediaAsset и опубликованные версии. **Приёмка:** замена медиа в Draft не меняет старые версии; недоступное медиа блокирует публикацию с понятной ошибкой.
- **TASK-DATA-05**: проверка доступа и безопасности. **Приёмка:** посторонний не может изменять Draft, публичный Player не выдаёт приватные черновики, rich text безопасен.

## Контроль ролей — обязательные приёмочные сценарии (D-021)

- Teacher видит/меняет/удаляет только собственные упражнения и медиа.
- Administrator управляет всеми библиотеками и аккаунтами.
- Запрещённые операции должны блокироваться сервером даже при ручном API-запросе.
- Общие Editor/Player не дублируются для ролей.
